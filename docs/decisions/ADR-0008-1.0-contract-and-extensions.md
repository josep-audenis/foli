# ADR-0008: The 1.0 contract and the extension API

- **Status:** Accepted when merged, task 12.1 (2026-11-19): the owner asked that day for Phase 12
  to be built task by task, each task merged after an agent's review, so this record is accepted
  by that review and not by the owner reading it, except one point left to the owner (schema
  versions in 1.x minors, under "The saved format"), which the owner accepted on 2026-11-20
  (12.11). Implemented in Phase 12 (12.2-12.11; 1.0.0); outcome below (12.12).
- **Context:** 0.6.0 is a Word-compatible editor with a lossless `.docx` round trip, but nothing in
  it is promised: `docs/api.md` says anything may change before 1.0. The generic model is open
  (`NodeSpec`, `MarkSpec`, `Schema`: `packages/core/src/model/schema.ts:9-56`), yet the editor is
  bound to one schema: `schema` is a module constant (`v3/schema.ts:482`), `parseContent` checks
  against it (`v3/document.ts:613-619`), and `EditorOptions` takes no schema
  (`state/editor.ts:87-102`). Plugins exist and every built-in feature uses them
  (`state/state.ts:20-54`, called an "internal extension point"), but the view has no node views,
  decorations or plugin views (`EditorViewOptions`, `view.ts:203-232`), handles some keys before
  any keymap (`onKeyDown`, `view.ts:3745-3826`), and `FoliToolbar` cannot be extended
  (`FoliToolbarProps`, `react/src/FoliToolbar.tsx:120`). Core's root re-exports four folders
  whole (`src/index.ts`, lines 10 and 40-42): 254 runtime names, with types about 300; the
  other four packages import 225 names from it. 29 `@internal` tags, no API report, no
  `stripInternal`.

## Question

What does 1.0 promise (public API per package, the saved format, semver, deprecation), and how
do apps add their own nodes, marks, commands, keys, decorations and toolbar items to a
Word-compatible editor without breaking the `.docx` round trip or losing content?

## Spike (`spikes/extension/`)

An app outside the packages declares `acme:mention`, an inline leaf with `id` and `label` drawn as
a chip `@label`, and `acme:topic`, a mark with `topic` (`src/spec.ts`), and a plugin whose keymap
inserts a mention (Ctrl+Shift+M) and toggles the topic (Ctrl+Shift+K) through core's
`toggleMark` (`src/extension.ts`). The packages are not changed: `vite.config.ts` patches their
source as it is served, adding the two types to the Word schema and letting the editing renderer
(`view/src/word/edit.ts`) ask a global registry how to draw a custom node or mark. That patch is
the stand-in for 12.3 and 12.4. `.docx` goes through `src/docx.ts`, a mapping on the document's
JSON (decided below). Run 2026-11-19, Playwright on Windows, Word 16.0 through COM:

| Experiment (`e2e/extension.spec.ts`, `src/*.test.ts`)                         | Chromium | Firefox  | WebKit  |
| ----------------------------------------------------------------------------- | -------- | -------- | ------- |
| Typed by its keys; saved JSON holds `acme:mention` and the marked text        | pass     | pass     | pass    |
| Drawn on the page (chip, dotted underline); the chip is one caret position    | pass     | pass     | pass    |
| Typing after the mark does not extend it (`inclusive: false`)                 | pass     | pass     | pass    |
| Undo removes the mark, then the mention; redo brings both; Backspace whole    | pass     | pass     | pass    |
| Saved, stored as a string, loaded behind 80 paragraphs: drawn on a later page | pass     | pass     | pass    |
| Exported to `.docx` and imported back in the page: the same node and mark     | pass     | pass     | pass    |
| Ctrl+A, Ctrl+C, Ctrl+V: pasted with the node and the mark                     | pass     | **fail** | skipped |

- **Firefox paste.** Playwright's Firefox gives the paste event `text/html` and `text/plain`
  only, not `application/x-foli+json` (logged in the page; Chromium gives all three). The HTML is
  read: the mention comes back as the text `@Ada Lovelace` with Word shading, the topic not at all.
  Nothing is lost as text, the node and the mark are. Real Firefox was not checked. WebKit is
  skipped as in the playground's clipboard tests (no clipboard data in Playwright's WebKit).
- **`.docx` in Node** (`src/docx.test.ts`, in `pnpm test`): a document with mentions (one bold,
  one in a table cell) and marked runs goes out through `exportDocx` and back through
  `importDocx` with the same custom nodes and marks; read without the mapping, the file keeps
  the content controls with their tags and text; `parseDocument` without the types throws
  `FoliDocumentError` (refused, not dropped); attributes that do not fit a tag throw.
- **Word** (`src/word.test.ts` with `FOLI_WORD=1`, `word.ps1`): five files (the sample, a mention
  whose tag is 255 characters, and the three files the e2e tests made in each engine). Word opened
  each and its `ContentControls` were compared, in order, with the controls Foli wrote: the same
  count, every custom node a plain text control (type 1, contents locked, its tag, the text
  `@label`), every marked run a rich text control (type 0, not locked, its tag, the run's text).
  Word then inserted "Word edit. " at the start and saved it (`SaveAs2`, `.docx`). Foli read each
  of Word's files back: every node and mark as it was, with its other marks (bold on a mention),
  the edit there. 5 of 5 passed, run again after the review of #121. Word keeps a 255-character
  tag.
- **Found on the way:** the engine needed no change beyond the schema. Commands, history,
  transactions, clipboard JSON and `.docx` controls already use `state.schema` (for example
  `review.ts:228`, `track.ts:277`), so a schema with more types works. The module constant is used
  only by `parseContent` (`v3/document.ts:614-615`), the run-property check
  (`v3/schema.ts:353`) and five modules of `@folijs/docx` (`import/tables.ts:7` and others).
  Without a node view, the renderer draws an unknown inline node as an empty span
  (`edit.ts:376-394`), and plain text (`clipboard.ts`, `leafText`) gives it no text.
- **Not in the spike:** a custom block node, a node view that splits across pages, find and
  tracked changes over custom content, an editor without the extension opening such a document
  (decided below as foreign nodes), decorations, plugin views, the toolbar.

## Decision

### Public API and its report

- **Each package's index lists its exports by name** (core's four `export *` go, 12.2). What the
  index exports and `docs/api.md` lists is the 1.x API. Everything else is not.
- **Two kinds of non-public names.** Names only one package uses are tagged `@internal` and
  stripped from the published `.d.ts` (`stripInternal`: checked with the repo's TypeScript 7.0.2,
  it drops tagged functions and interface members). Of the 225 core names the other packages
  import, those that are not public (the Word context, the resolver, layout helpers) move to a
  second entry, `@folijs/core/internal`, documented as without any promise.
- **One copy of core, at the same version.** `@folijs/view`, `react`, `docx` and `pdf` declare
  `@folijs/core` (and `@folijs/view` where they use it) as `peerDependencies` with
  `workspace:*`, published as the exact version, instead of `dependencies` (`workspace:^` today).
  Two copies of core in an app would break silently: `instanceof` on model classes, `PluginKey`
  identity, a schema's node types. With exact peers a mismatch fails at install, and the internal
  entry is safe because every package runs with the core it was built with. They are already
  released together (`.changeset/config.json`, `fixed`). 12.2 makes the change.
- **API report** per package: `packages/<name>/api-report.d.ts`, the package's built
  `dist/**/*.d.ts` joined in path order, source-map comments removed. `pnpm check` builds,
  writes the report to a temporary file and fails when it differs from the committed one;
  `pnpm api:update` rewrites it, so a change to the API is a reviewed diff. A small script, no
  new dependency.
- The same script fails on a **forgotten export**: a name a module exports, the index does not,
  and that is not `@internal` (so the report stays the public surface, not every helper).
- What 1.x keeps per package, in short (the list by name is 12.2's `docs/api.md`):
  - `@folijs/core`: documents (`FoliDocument` and its JSON types, `parseDocument`,
    `createDocument`, `SCHEMA_VERSION`, `FoliDocumentError`), `createEditor` and `Editor`, the
    named commands, the extension API below, and for plugins the model (`Node`, `Fragment`,
    `Slice`, `Mark`, `Schema`, `ResolvedPos`), `EditorState`, `Transaction`, the selections,
    `Transform`, `Step`, `StepMap`, `Mapping`.
  - `@folijs/view`: `EditorView` and its options, `renderDocument`, the clipboard helpers, the
    view extension API below.
  - `@folijs/react`: the components, their props, the hooks, the toolbar items.
  - `@folijs/docx`: `importDocx`, `exportDocx`, their options and reports, `packageImages`.
  - `@folijs/pdf`: `exportPdf` and its options.
  - CSS: the 13 `--foli-*` variables and the documented class names (`docs/styling.md`).

### The saved format

- **Every 1.x reads every earlier format** without loss: v1 to v5 (0.1.0 to 0.6.0) and every format
  a 1.x minor adds. 12.11 keeps a fixture per version that loads and saves in every release.
- **A 1.x minor may bump `SCHEMA_VERSION`**, only by adding (node types, attributes, envelope keys),
  with a migration from the version before; a change that removes or changes the meaning of saved
  content waits for 2.0. This is not "v5 frozen for 1.x" as the task text put it: the Word model
  still grows (charts, shapes, text boxes and equations are opaque today), and freezing would
  leave all of it opaque until 2.0. Content 1.x does not model stays opaque and round-trips, as now.
- **A document is saved with the lowest schema version its content needs**, never below 5 (1.0's):
  a document saved by 1.3 that uses nothing added after 1.0 says `schemaVersion: 5`, and 1.0 (a
  server running `exportPdf`, say) reads it. `getDocument` and `exportDocx`'s JSON side compute
  it with the same per-version table `parseDocument` already uses to refuse later content in a
  document that claims an earlier version (`laterNode`, `laterSection`, the envelope keys:
  `v3/document.ts:470-490`). Checked by a test per version: a document using only that version's
  content saves with it and passes `parseDocument` as that version; one using a later node says
  the later one. A wrong table fails these tests, never a reader.
- **An older 1.x refuses a document that needs a newer version** with a `FoliDocumentError` that
  says so, as `parseDocument` already does (`v3/document.ts:499-505`); it never drops what it does
  not know. The changeset of a minor that bumps the version says what content older 1.x cannot
  read, as 0.6.0's did.
- **Accepted by the owner (2026-11-20, 12.11):** a 1.x minor may add a schema version, and a
  document is saved with the lowest version its content needs. This departs from the roadmap's
  first wording, "schema v5 frozen for 1.x"; the review had accepted the rest of this record.
- Apps that walk the JSON must ignore node and mark types they do not know: new ones arrive in
  minors.
- Custom node and mark types are the app's and never change `SCHEMA_VERSION`.

### Semver and deprecation

- **Breaking** (2.0 only): removing or renaming an export, a prop or an option; narrowing what a
  function accepts; changing what it returns or does for input that worked; removing a CSS
  variable or documented class; a saved-format change as above.
- **Minor:** new exports, options, props, commands, keys; new members of types the packages
  return (node types, `ControlJSON.kind`, report reasons): switches over them need a default.
  Patch: fixes, including making an output match Word where it did not.
- **Deprecation:** `@deprecated` JSDoc naming the replacement (editors strike it through); a
  one-time `console.warn` per name where the old path runs anyway and the check is cheap, only
  when `globalThis.process?.env?.NODE_ENV !== "production"`; listed in the changeset and the
  changelog; kept until the next major at least. `docs/api.md` marks it.
- Before 1.0 nothing changes: 0.x minors may still break, as `docs/api.md` says.

### Custom nodes and marks

- **Declared as an extension:** `{ name, nodes?, marks?, plugins? }`, given to
  `createEditor({ extensions })` and to `parseDocument(document, { extensions })`. Core builds the
  editor's schema from the Word schema and the extensions' types (the spike's
  `new Schema({ nodes: { ...word, ...custom } })`), and `parseContent` checks against that
  schema instead of the constant.
- The Word schema and its types stay as they are; an extension only adds.
- **Names have a namespace:** `<ns>:<name>`, lowercase letters, digits and `-`. Word's types never
  have a colon, so they cannot clash; a name that is not namespaced or is taken twice throws when
  the editor is made.
- **What a type may be in 1.x:** an inline leaf (group `inline`), a block leaf (group `block`), or
  a mark. Attributes as in `NodeSpec` with a `validate` each (`model/attrs.ts`). A node spec adds
  `text(attrs)`: the text it stands for in plain text, find, the clipboard and `.docx`. No custom
  container nodes (content expressions) in 1.x: Word has nothing to write them as, and the page
  flow would need a layout per container.
- **Stored** as ordinary node and mark JSON in the envelope's content, stories and comments, by
  type name. Nothing else in the envelope.
- **Without its extension** a custom type is never dropped and does not stop the document from
  loading: `parseDocument` turns a namespaced type it does not know into a foreign node
  (`foreignInline`, `foreignBlock`) or a foreign mark holding the original JSON (size-limited,
  checked as plain JSON), drawn as a labelled box like opaque content, selected and deleted whole,
  written back exactly by `getDocument` and to `.docx` the same way. The saved JSON does not
  carry `text(attrs)`, so in `.docx` a foreign node keeps the text its control had when it was
  imported (held on the foreign node, in memory); one loaded from JSON writes its type in brackets
  (`[acme:mention]`), and the tag keeps everything that matters. Foreign types live only in memory
  and are never saved, so they are not a format change. The spike shows only today's
  refusal; this part is 12.3's to build and test.
- **Laid out and drawn** by node views (below). Without one, a custom node is drawn as a foreign
  node is, from `text(attrs)`.
- **Clipboard:** the Foli JSON carries them (works where the browser gives it back); the HTML
  carries them too, as `data-foli-node` and `data-foli-mark` attributes holding the JSON on the
  drawn element, read back when the schema has the type. That is what Firefox's paste needs
  (spike). Plain text gets `text(attrs)`.
- **In `.docx`: a content control tagged with the type and attributes.** A custom node is a plain
  text control (`w:sdt` with `w:text`, contents locked) holding `text(attrs)`; a run of a custom
  mark is a rich text control around that run (one per paragraph it crosses); a block node a
  block control around one paragraph with its text. The tag is `foli:` and
  `{"node"|"mark": type, "attrs": …}` as JSON. Import turns such controls back into the node or
  mark, whether or not the extension is loaded (foreign without it). Generic: no `.docx` code per
  type. The spike passed this through Word for inline nodes and marks; block nodes are 12.3's to
  test.
- **Tags have at most 255 characters** (`checkControl`'s `tag`, `v3/document.ts:902`; Word kept
  255 in the spike). A node or mark whose tag would be longer makes `exportDocx` throw a
  `DocxError` naming it, never cut: an app keeps large data elsewhere and an id in the attributes.
- Word users see the controls (a locked chip they can delete, a frame around a topic) and keep
  them through their edits. Text typed in Word into a marked control gets the mark when read back
  (that is how the mapping is written; the spike did not type into one in Word).

### Plugins, view hooks, commands and keys

- **`PluginSpec` is frozen** as it is (`key`, `state.init`/`apply`, `filterTransaction`,
  `appendTransaction`, `keymap`), plus `commands` (below). `Plugin` and `PluginKey` become public;
  user plugins keep running before the built-ins (`editor.ts:454-465`).
- **View hooks live in `@folijs/view`** (core has no DOM): a `ViewExtension` extends core's
  extension with `nodeViews` (draw a custom node: measured and placed by the flow, `split: false`
  keeps it whole on one page), `markViews` (style a marked run), `decorations(state)` (inline and
  node decorations: classes and attributes on ranges, never document content) and `view(editorView)`
  returning `{ update?, destroy? }`. The editor keeps its extensions, so the view and `FoliEditor`
  take the same list once (`extensions` prop). Find's matches and the selected field may move onto
  decorations where it is simpler (12.4).
- **Commands:** a plugin's `commands` maps names to command factories `(...args) => Command`;
  `editor.commands.<name>(...args)` runs one, `editor.can(factory(...args))` dry-runs it, as
  built-in commands do today (`editor.ts:188`, `:371`). A name taken twice throws when the
  editor is made.
  The names are typed through an interface apps augment:

  ```ts
  declare module "@folijs/core" {
    interface FoliCommands {
      insertMention(id: string, label: string): boolean;
    }
  }
  ```

- **Keys the view handles before the keymaps** (`view.ts:3745-3826`), and what becomes of them:

  | Keys                                                                                 | Where today (`view.ts`)                                                                     | 1.x          |
  | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- | ------------ |
  | Ctrl+Home, Ctrl+End (and with Shift)                                                 | `documentEdgeKey` (3840)                                                                    | overridable  |
  | F9, Alt+F9                                                                           | `fieldKey` (2148)                                                                           | overridable  |
  | Alt+Down (a control's list)                                                          | `controlKey` (2035)                                                                         | overridable  |
  | Ctrl+Alt+F, Ctrl+Alt+D, Shift+Alt+N                                                  | `noteKey` (3829), story (2340)                                                              | overridable  |
  | Ctrl+F, Ctrl+H, Ctrl+G, F3, Shift+F3, Ctrl+Shift+F5                                  | `navigationKey` (1971)                                                                      | overridable  |
  | Left, Right (and with Shift) at page splits, list numbers, field parts, placeholders | `crossFragmentEdge` (3886), `crossListNumber` (3938), `skipFieldParts` (2128), `controlKey` | reserved (1) |
  | Escape in a header, footer or note                                                   | `onKeyDown`, story (2340)                                                                   | reserved (2) |
  | Tab, Shift+Tab after Escape or when read-only                                        | `onKeyDown` (3781)                                                                          | reserved (2) |
  | Ctrl+Shift+V                                                                         | `onKeyDown` (3777)                                                                          | reserved (3) |
  | Escape while dragging or resizing a picture                                          | `onDragKey` (3407), `onResizeKey` (3521)                                                    | reserved (4) |
  | Keys inside a control's list or date pop-up                                          | `word/controls.ts` (363, 415)                                                               | reserved (4) |
  | Any key while composing (IME)                                                        | `onKeyDown`                                                                                 | reserved (5) |

  (1) Caret fixes for the pages' DOM, acting only where the browser would move wrong; a keymap
  binding of a plain arrow runs wherever they do not act. (2) The way out of a nested editing host
  or of the document: no keyboard trap. (3) It only marks the next paste as plain text and does
  not take the key. (4) The keys of a gesture or a pop-up widget, not of the document. (5) An
  input method owns the keys until it commits.

  Shift+arrows in tables and Up/Down beside rules or across cells already run after the keymaps
  (`view.ts:3786` before `3794-3825`), so they are overridable today; "Starts from" said
  otherwise. The keys made overridable become a built-in keymap in `@folijs/view` (some of their
  commands need the layout), after the user's plugins like every built-in.

- **Toolbar:** `FoliToolbar` takes `items` (groups of items); the built-in items are exported by
  name, so an app adds, removes and regroups them. An item runs a command and asks
  `editor.can` for its state, as the built-in buttons do. Menus share the code where they can
  (12.6).
- **History and collaboration:** `history()` and its options, `undo`, `redo`, `undoDepth` and the
  `addToHistory`, `closeHistory`, `joinHistory` metadata are public; the plugin's state stays
  internal (`history.ts:15` already says so), so collaboration can change it. Collaboration is
  not part of 1.0: steps, maps and mapping are public, which is what a later package needs.

### Performance, docs site, Rust

- **Performance without hosted CI:** `pnpm bench` runs the layout, keystroke, find, `.docx` import
  and export and PDF benchmarks and compares each median with a committed baseline for that
  machine and engine (`bench/baselines/<machine>.json`, the machine named by the runner); each
  baseline carries its threshold, set in 12.7 from the measured run-to-run spread (the micro
  benchmarks vary up to ±40% on the owner's laptop: `docs/benchmarks.md`). A run past a threshold
  fails. It runs before every release (12.11 for 1.0) and on any change meant to be faster; not
  in the pre-push hook (minutes in three engines). A hosted workflow only if the owner turns one on.
- **Docs site:** built in `apps/site` with Vite from `docs/*.md` at build time, so the pages are
  the files in the repo and cannot drift; markdown rendered by `marked` (MIT, 18.2.1, no
  dependencies) as a devDependency of the private site; the API reference from the 12.2 reports;
  live examples are the site's own pages running the packages; search, if any, an index the build
  writes, no service. Host: where the landing page is, `foli.josepaudenis.com` (the repository's
  homepage), served by Cloudflare. Corrected in 12.12: this said nothing deploys it and the
  deploy stays the owner's step; in fact a Cloudflare Pages project connected to the repository
  builds every pushed commit and publishes `main` (its "Cloudflare Pages" checks on GitHub; the
  build settings live in Cloudflare's dashboard, not in the repository: contributing.md,
  "The site").
- **Rust and WebAssembly:** not planned. Only if a benchmark shows a need JavaScript cannot meet.

## Options rejected

- **Custom XML markup in the body (`w:customXml`) for custom content:** Word stopped keeping
  custom XML markup in documents in 2010 (the i4i patent ruling), so it would be lost on the
  first save. Not tested in the spike.
- **A custom XML part with the attributes, referenced from the body:** survives Word but needs a
  second reference (a bookmark or a control) anyway; the control's tag alone carried every case
  the spike tried. Kept in mind if 255 characters prove too few.
- **Refusing custom content in `.docx`:** the acceptance asks for it to go through, and the
  control keeps it visible to Word users.
- **A free schema (apps replace the Word schema):** every command, renderer and the `.docx`
  package assume Word's types; extensions add to it instead.
- **Refusing a document whose extension is missing:** what the spike's packages do today; a
  viewer, `exportPdf` or another app could then not open it at all. Foreign nodes keep it.
- **v5 frozen for all of 1.x:** see the saved format (rejected here; the owner agreed on
  2026-11-20).
- **API Extractor** for the reports: a tool and a dependency for what a short script and the
  compiler's own `.d.ts` give.
- **Hosted CI for benchmarks:** shared runners vary more than the thresholds; the owner's machine
  is the reference, as for the Word harnesses.

## Consequences

- 12.2 has to sort 254 core names into public, `internal` entry and `@internal`, and tag the
  view's and docx's internal helpers; the report starts large and then changes only on purpose.
- Core's `schema` stops being the one schema: `parseContent`, the docx package and every
  `schema.nodes.x` in code that runs on an extended editor must take the state's schema (the
  three users of the constant above).
- Find, tracked changes, comments and fields must treat custom leaves as atoms with
  `text(attrs)`; the spike did not exercise them.
- `.docx` written with custom content shows content controls in Word, which is visible to Word
  users; a document's tags are readable by anyone with the file, so apps should not put secrets in
  attributes.
- Exact peer versions mean an app installs and upgrades the packages together, which `fixed`
  releases already imply. npm 7+ and pnpm install peers themselves; other managers need them
  listed, so the install lines in `docs/getting-started.md` name every package used (`@folijs/view`
  joins the React line in 12.9). The examples already list core and view
  (`examples/*/package.json`).

## Outcome (12.12, 2026-11-20)

- **Public API as decided.** Each index lists its exports by name (core 346 public names, view 14,
  React 19, docx 27, PDF 8 at 12.2, more since with the extension API); 37 names on
  `@folijs/core/internal`; 362 `@internal` tags stripped from the published types; an API report
  per package (`packages/<name>/api-report.d.ts`), compared in `pnpm check` by `scripts/api.mjs`,
  which also fails on a forgotten export, `export *` in an entry, published types that do not
  compile alone and a public entry importing the internal one. Core is an exact peer of the
  other packages. `docs/api.md` marks internal names; the rest is the 1.x API.
- **Saved format as decided,** with the point the owner accepted on 2026-11-20: v5 is 1.0's
  version and the lowest a document is saved with; a fixture per 0.x version, saved by the
  release that wrote it (`packages/core/fixtures/formats/`), loads and saves in core and through
  `.docx` in every `pnpm check`. Nothing computes a lower version yet: there is only v5 in 1.x so
  far, and the first minor that adds one builds the per-version table and its tests.
- **Semver and deprecation** in [deprecation.md](../deprecation.md); nothing is deprecated in
  1.0.
- **Custom nodes and marks as decided** (12.3): namespaced leaves and marks through `Extension`,
  foreign nodes and the `foreign` mark when the extension is missing, `.docx` content controls
  tagged `foli:` (255 characters, longer refused); Word 16 reads and edits them back
  (`extension-roundtrip.mjs`). Changed from the decision: the clipboard HTML carries a copy's
  whole JSON on one wrapper instead of per-element attributes; a foreign node's `.docx` text
  stays in memory only.
- **Plugins, view hooks, commands, keys and toolbar as decided** (12.4-12.6): `ViewExtension`
  (node views split across pages, mark views, decorations, plugin views, all through `h`, which
  refuses unsafe output); `PluginSpec.commands` and `FoliCommands`; every key the view takes
  itself overridable (run at the `viewKeys` marker) or reserved, listed per platform in
  [keyboard.md](../keyboard.md); toolbar `items`, `toolbarItems`, `defaultToolbarItems`,
  `useCommand`. Changed: the view's overridable keys are a table run at the marker, not a
  `Plugin`, so `editor.handleKey` does not run them; `plugins` and `extensions` stay read once,
  with a development warning.
- **Performance as decided** (12.7): `pnpm bench` with a committed baseline per machine, run
  before each release. Of three runs in 12.12 the first failed 12 metrics on a busy machine, the
  second passed all 51 and the third (`--update`) failed only Chromium's re-flow at 200 sections
  (+110%), a noisy metric; the baseline is the second run's. The Phase 5 targets are missed at 100 pages (handler, first layout,
  re-flow: [benchmarks.md](../benchmarks.md#10-numbers)); the owner decided on 2026-11-20 that
  this does not block 1.0. No benchmark asks for Rust or WebAssembly.
